# 南非停电通知接口升级 3.0 测试方案

> 方案版本：V1.0  
> 编写日期：2026-08-19  
> 测试对象：roulette 南非停电计划入库、通知及储能强充链路  
> 外部数据源：EskomSePush Business API 3.0  
> 重要期限：EskomSePush API v2.0 将于 2026-09-01 停止服务

## 1. 测试背景

EskomSePush 将 Business API 从 2.x 升级到 3.0。3.0 把“区域 Area”和“停电时刻表 Schedule”拆成两个资源：

- v3 Area ID 使用下划线，例如 `za_gt_jhb_fourways_4pef`；
- v3 Schedule ID 使用短横线，例如 `eskde-10`；
- 原 `/area` 不再直接提供完整停电计划；
- 新增 `/schedule` 返回 `events` 和按日期、Stage、slot 组织的完整时刻表。

本项目保留数据库中的 v2 `block_id`，运行时把它转换成 v3 Schedule ID，请求 `/schedule` 后再转换为旧数据库格式。下游 rice、APP 展示、停电通知、强充和恢复逻辑原则上保持不变。

## 3. 测试目标

1. 确认运行中的接口已从 `/business/2.0` 切换到 `/business/3.0`。
2. 确认 `/status` 和 `/schedule` 的请求、认证、响应解析及异常处理正确。
3. 确认存量 v2 `block_id` 能正确转换为 v3 Schedule ID，且数据库原 ID 不变。
4. 确认 v3 raw schedule 能转换成现有下游兼容的固定 8 级二维数组。
5. 确认同一 Schedule ID 每轮只请求一次，并能回填所有对应的旧 `block_id`。
6. 确认第三方请求或数据异常时不会写入空数据、半份数据或覆盖有效旧数据。
7. 确认通知、强充、跨天恢复和 APP 展示行为在升级前后保持一致。
8. 确认配额、重试、日志脱敏、任务开关和上线止损机制可用。
9. 确认依赖旧 `/areas_search.region` 的 `addregion` 无法被误执行。

## 4. 测试对象与业务链路

```text
XXL-JOB: eskominfoJob
        ↓
查询 plants.block_id
        ↓
v2 block_id → v3 schedule_id
        ↓
按 schedule_id 去重
        ↓
EskomSePush /business/3.0/schedule
        ↓
raw schedule → 旧 8 级 HH:mm-HH:mm 格式
        ↓
按原 block_id 回填并入库
        ↓
eskomPushMessageJob
        ↓
通知 / 强充 / 恢复任务 / rice 与 APP 展示
```

同时需要回归：

```text
EskomSePush /business/3.0/status
        ↓
国家级 Eskom Stage / 可选市政 Stage
        ↓
现有停电状态业务逻辑
```

## 5. 测试范围

### 5.1 本次范围内

- 外部 API 基础地址、版本及 Token 请求头；
- `GET /business/3.0/status`；
- `GET /business/3.0/schedule?id=...`；
- `/schedule` 的 `test=current`、`test=future`；
- HTTP 状态码、超时、非 JSON、限流响应头和重试；
- v2 `block_id` 到 v3 Schedule ID 的转换器；
- raw schedule 到旧 8 级二维数组的转换器；
- Schedule ID 去重、批量同步、回填和入库；
- 旧数据保护、重复执行和事务完整性；
- `eskominfoJob`、`eskomPushMessageJob`、`addregion`；
- 通知、强充、跨天恢复、rice/APP 展示回归；
- 发布任务开关、手工验收、告警和止损。

### 5.2 关联验证但非核心发布阻塞项

- `/area` 的 Area ID 与 `schedules` 返回；
- `/areas_search` 的新 ID 和缺少 `region` 的兼容性；
- `/areas_nearby` 基础冒烟；
- `load_reduction` 与 `loadshedding` 的类型隔离；
- `/api_allowance` 仅确认未新增依赖，因为该接口已弃用。

### 5.3 本次范围外

- v3.1 Beta 的 Reports、Chats 等社区故障能力；
- EskomSePush 服务端算法和数据准确性的内部实现；
- 未经供应商授权的外部 API 压力测试；
- `addregion` 的 v3 重构或区域树重新初始化；
- 数据库 ID 迁移、rice 改造或 APP 新功能。

## 8. 测试策略

### 8.1 静态检查

- 搜索运行代码、配置、脚本、定时任务中的 `/business/2.0/`；
- 确认 3.0 URL 常量和新增 `/schedule` URL；
- 确认请求头使用 `token`，不是 `Authorization: Bearer`；
- 确认 Token 不参与 URL、普通日志、异常堆栈和 APM tag；
- 确认新增测试类、fixture 和 CI 测试步骤存在且会实际执行；
- 确认 `addregion` 在 job 和 service 两层均硬禁用。

### 8.2 接口契约测试

- 使用真实接口做最小量冒烟，确认当前官方契约；
- 使用 Stub 构造边界和异常，避免耗尽真实额度；
- 不将 OpenAPI 单个 example 当成完整必填 Schema；
- 验证新增未知字段不影响解析，关键字段缺失时按失败策略处理。

### 8.3 数据转换测试

- 转换器采用表驱动单元测试；
- 每个 fixture 同时断言成功输出或明确失败类型；
- 重点验证时区、跨天、Stage 累计并集、排序和去重；
- 非法数据必须验证数据库旧值保持不变。

### 8.4 批量同步与数据库测试

- 用多 block 对一 schedule 的数据验证去重；
- 注入部分成功、部分失败，验证事务边界；
- 对入库前后进行快照对比；
- 重复触发同一轮，验证幂等性和无重复数据。

### 8.5 端到端回归

- 选择隔离测试电站走完整链路；
- 覆盖通知前强充、停电开始、跨天恢复、Stage 变化和无停电事件；
- 同时观察 DB、任务、消息、设备指令和 APP 展示。

## 10. 数据库验证要求

由于原技术文档没有给出实际时刻表表名、字段名和 SQL，以下查询需由开发或 DBA 在执行前补齐并评审：

1. 统计非空 `plants.block_id` 总数和 distinct 数；
2. 按转换规则统计 distinct Schedule ID 数；
3. 查找空、少段、下划线及其他异常 `block_id`；
4. 任务执行前备份或快照测试范围内的旧时刻表；
5. 验证入库结果固定包含 Stage 1～8；
6. 验证所有时间段符合 `HH:mm-HH:mm`；
7. 查找重复 slot、空值、非法时间和无法表达的跨两天数据；
8. 验证同 schedule 的多个旧 block ID 回填结果一致；
9. 验证失败 schedule 的旧数据更新时间和值均未被错误覆盖；
10. 验证 `ns_region` 和 `plants.block_id` 在升级过程中没有 ID 迁移。

执行数据库验证时应遵守：

- 联调和生产验收查询默认只读；
- 先限定环境、表和测试电站范围；
- 禁止执行未经评审的全表更新或删除；
- 查询结果需脱敏并随测试报告留档。

## 11. 配额测试与预算

### 11.1 配额公式

单轮基础请求量：

```text
单轮基础请求量 = distinct schedule_id 数 + status 请求数
```

最坏请求量需再考虑：

```text
最坏请求量 = 基础请求量 + 发生 5xx 的请求重试量 + 手工联调请求量
```

测试前应根据真实调度频率计算每日用量，并给手工验收、异常重试和临时排查预留空间。历史记录“273 个 distinct block 合并为 72 个 schedule、配额 2,500/天”只能作为参考，实际断言以当日数据和响应头为准。

### 11.2 配额验证注意事项

- 真实接口测试禁止无控制的循环或 Runner；
- `test=current/future` 官方声明不扣 credit，可比较调用前后 used/remaining；
- 并发环境下配额可能被其他任务同时消耗，不应机械断言 remaining 必须逐次减 1；
- 429 后必须依据 `x-ratelimit-reset`，不能固定立即重试；
- 生产 Token 不用于压力测试。

## 14. 上线验证与止损

### 14.1 上线顺序

1. 确认 `eskominfoJob` 停用；
2. 暂停全量推送任务；
3. 发布应用；
4. 核对版本、配置和 3.0 Base URL；
5. 手工触发一次 `eskominfoJob`；
6. 核对请求数、状态码、限流头、转换数和数据库格式；
7. 用测试电站验证通知、强充、恢复和 APP 展示；
8. 恢复 `eskominfoJob` 调度；
9. 确认一轮稳定后恢复全量推送；
10. 连续观察至少一个完整调度周期。

### 14.2 立即止损条件

出现以下任一情况，应立即停用 `eskominfoJob`，保持或恢复推送安全状态，并通知负责人：

- 401、403 或 Token 被禁用；
- 429 且当前周期无法继续安全执行；
- 达到约定阈值的批量 404；
- schedule 大量解析失败；
- 入库不是固定 8 级或出现非法时间格式；
- 旧有效数据被空数据/半份数据覆盖；
- 请求数显著高于 distinct schedule 数；
- 出现大范围重复通知或错误强充；
- Token 泄漏到任何日志或报告。

### 14.3 回退后的验证

- 确认任务已停止且不再消耗额度；
- 确认数据库未继续被异常结果更新；
- 确认旧有效时刻表仍可被下游使用；
- 确认没有残留的重复通知、强充或恢复任务；
- 保存日志、请求统计和数据库对比证据；
- 注意 v2 将于 2026-09-01 下线，不能把长期回退到 v2 作为最终解决方案。
