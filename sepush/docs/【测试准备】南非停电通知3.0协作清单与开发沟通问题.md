# 南非停电通知 3.0：测试准备、协作方式与开发沟通清单

> 文档用途：汇总当前已经具备的测试条件、仍需开发补充的信息、建议申请的权限，以及接下来端到端测试的协作方式。  
> 更新日期：2026-08-20  
> 测试方式：不分析源码，以黑盒 API、数据库结果、Job 执行结果和界面表现完成端到端验证。

## 1. 当前结论

本任务可以由测试主导完成端到端验证，不要求测试人员先完全掌握南非停电业务，也不要求提供代码仓库。

本次主要采用两种方法：

1. **升级前后对比**：相同电站、相同停电计划下，数据库、通知、强充、恢复和 APP/rice 展示行为应保持一致。
2. **关键规则验证**：重点确认 v3 API、ID 转换、8 级计划、跨天、请求去重、异常时旧数据保护和任务止损。

需要开发配合补充环境入口、表结构、测试电站和少量业务规则。测试人员负责实际操作，我负责给出步骤、SQL/API 检查内容、预期结果、证据要求以及测试结论。

## 3. XXL-JOB 是否需要权限

建议有权限，但不需要管理员权限。

### 3.1 测试环境建议申请的最小权限

- 查看 `eskominfoJob` 和 `eskomPushMessageJob` 的配置、状态及执行历史；
- 查看 Job 执行日志；
- 手工触发一次 Job；
- 停止和恢复 Job 调度；
- 查看触发时间、执行机器、开始/结束时间和成功/失败状态。

不建议为了本任务申请：

- 删除 Job；
- 修改执行器或业务参数；
- 修改其他项目 Job；
- XXL-JOB 系统管理员权限。

### 3.2 生产环境权限建议

- 优先只读；
- 停止、恢复和手工触发由运维或发布负责人执行；
- 如果测试必须直接操作，应使用有审计记录、限定 Job 范围的临时权限。

### 3.3 没有权限时的替代方式

由开发或运维共享屏幕/代操作也可以，但必须提供：

- 操作时间；
- 操作的 Job 名称；
- 触发前后状态；
- 执行结果和日志；
- 是否恢复调度的确认。

## 4. `block_id` 在哪里

技术文档已经明确：

- 用户电站的历史区域 ID 在 **`plants.block_id`**；
- 区域树的历史 ID 也存在 **`ns_region`** 中；
- rice 会按旧 `block_id` 做等值 JOIN；
- 本次升级只能在代码运行时把旧 ID 转成 Schedule ID，不能修改 `plants.block_id` 或把 `ns_region` 换成 v3 下划线 ID。

示例：

```text
plants.block_id（数据库保持不变）：eskde-10-fourways
请求 3.0 /schedule 时使用：        eskde-10
```

需要向开发确认 `plants` 所在的实际数据库/schema，以及怎样通过电站 SN、plant ID 或用户账号定位测试电站记录。

## 5. 原技术文档写了哪些表，缺少哪些表

### 5.1 已写明

| 表/字段 | 已知用途 |
| --- | --- |
| `plants.block_id` | 电站选择的历史 v2 区块 ID，是 `eskominfoJob` 的输入 |
| `ns_region` | APP 南非地区树的存量区域数据；`addregion` 原来向这里写入 |

### 5.2 原文没有写明

- 停电时刻表最终写入哪张表、哪个字段；
- 固定 8 级二维数组实际保存为 JSON、文本还是其他结构；
- 哪个字段表示数据日期、更新时间和原 `block_id`；
- 推送消息记录保存在哪张表；
- 强充指令和恢复任务保存在哪张表或平台；
- 如何通过 plant ID/SN 关联上述记录；
- Job 执行成功后可使用的验收 SQL。

原技术文档的“相关查询 SQL”章节只有空代码块，因此以上信息必须向开发补充。

## 6. 界面端到端验证收敛

界面验证不需要笼统检查整个 APP，只需要围绕一个测试电站确认以下四个结果。

### 6.1 停电计划展示

需要确认：

- 从哪个 APP/rice 页面进入；
- 页面显示的停电日期、开始时间、结束时间和 Stage；
- 页面时区；
- 数据更新后是否需要刷新、重新登录或等待缓存；
- 跨天计划在页面如何显示，例如 `20:00-00:30` 是否拆成当天和次日两段。

### 6.2 停电通知

需要确认：

- 通知通过 APP Push、站内消息还是其他渠道发送；
- 在停电前多少分钟发送；
- 通知标题、时间、Stage 和电站信息应显示什么；
- 相同计划重复执行 Job 是否会重复通知；
- 在哪里能查看推送记录。

### 6.3 强充

需要确认：

- 停电前多少分钟开始强充；
- 强充目标 SOC 或目标模式；
- 在哪个电站/设备页面查看当前模式、充电状态和 SOC；
- 没有真实设备时，用什么平台记录或数据库记录代替；
- 相同计划是否只下发一次。

### 6.4 恢复

需要确认：

- 停电结束后恢复什么：充电模式、原计划、设备设置还是任务状态；
- 跨午夜时恢复任务是否安排到次日；
- 在哪个页面确认恢复成功；
- 停电计划发生变化或取消时，旧恢复任务如何处理。

## 7. 第一轮必须向开发确认的问题

以下问题足够支持第一轮正常链路端到端测试，应优先询问。

### 7.1 环境和 API

1. 本次 3.0 升级部署在哪个测试环境？当前版本号或发布时间是什么？
2. EskomSePush Token 由谁配置？测试环境当前配额是多少？
3. 能否提供一个已验证可用的 Schedule ID，或者一个有效的南非测试电站？
4. 测试环境是否直接访问真实 EskomSePush，还是经过公司网关/代理？

### 7.2 XXL-JOB

5. `eskominfoJob` 和 `eskomPushMessageJob` 分别位于哪个 XXL-JOB 环境、执行器和 Job ID？
6. 两个 Job 的 cron、正常执行顺序和单轮预计耗时是多少？
7. 测试环境能否给测试账号开放查看、手工触发、停止和恢复权限？
8. 手工触发 `eskominfoJob` 后，应该从哪里确认请求数、成功数和失败数？
9. `addregion` 对应哪个 Job？如何验证它已经禁止执行？

### 7.3 数据库

10. `plants` 位于哪个库/schema？如何通过测试账号、plant ID 或 SN 定位测试电站？
11. 停电计划写入哪张表、哪些字段？请提供一条执行前后的查询 SQL。
12. 8 个 Stage 在库中的实际格式是什么？请提供一条正常数据样例。
13. 推送记录、强充指令、恢复任务分别保存在哪里？如何按测试电站查询？
14. Job 失败时，如何通过数据库确认旧数据没有被覆盖？

### 7.4 界面和测试电站

15. 提供哪个测试账号和南非测试电站？是否会连接真实设备或影响真实客户？
16. 在 APP/rice 的哪个页面查看停电计划？请演示一次正常页面路径。
17. 通知在哪里接收，正常应提前多久？
18. 强充在什么时间触发、目标是什么、在哪个页面确认？
19. 停电结束后恢复什么，在哪个页面确认？
20. 是否有一个跨午夜计划的测试电站；如果没有，能否通过测试数据或 Mock 构造？

## 8. 第二轮再确认的问题

这些问题用于异常、限流和上线验收，可以在正常链路跑通后再问。

1. 401、403、404、429、5xx 分别如何告警？
2. 5xx 是否确实为初次请求后最多重试 2 次？网络超时是否重试？
3. 多少个 404 算“批量 404”，达到阈值后谁负责停 Job？
4. 单个 Schedule 失败时，是只保留该 Schedule 旧数据，还是整轮不入库？
5. `x-ratelimit-reset` 在哪里记录，429 后如何恢复任务？
6. 日志从哪里查看？Token 是否已经脱敏？
7. 相同 Schedule ID 去重后的请求数量在哪里查看？
8. 上线时谁负责停止、手工触发和恢复 Job？
9. 验收失败时是否只停用 Job，还是还需要应用回滚？
10. 完整观察周期按哪个 Job 的 cron 计算？

## 9. 建议让开发现场演示一次的业务场景

为了最快建立业务理解，建议安排一次 20～30 分钟演示，只演示以下一条正常链路：

```text
选择测试账号和测试电站
        ↓
查询 plants.block_id
        ↓
在 XXL-JOB 手工触发 eskominfoJob
        ↓
查询停电计划入库结果
        ↓
在 APP/rice 页面查看计划
        ↓
说明通知何时触发
        ↓
说明强充和恢复在哪里查看
```

演示时需要记录：

- 测试账号、plant ID/SN 和 `block_id`；
- 操作页面路径；
- 两个 Job 的位置和名称；
- 查询 SQL；
- 一条正常计划的数据库值；
- 通知、强充、恢复的预期时间和观察入口。

这次演示完成后，测试人员不需要掌握全部历史逻辑，就可以按同一路径完成升级前后对比和异常扩展测试。

## 10. 双方协作方式

### 10.1 测试人员负责

- 向开发获取上述环境、权限、表结构和测试电站信息；
- 在测试环境操作 XXL-JOB、数据库和 APP；
- 将结果以脱敏文本、JSON、表格或截图提供；
- 确保测试只影响测试账号和测试电站；
- 未经发布负责人允许，不在生产环境手工写库或操作其他 Job。

### 10.2 我负责

- 根据开发反馈更新测试范围和预期；
- 为每一轮测试提供准确操作步骤；
- 编写 API 请求、数据库只读 SQL 模板和检查规则；
- 分析 API 响应、数据库结果、Job 日志和界面截图；
- 识别缺陷、证据不足和业务待确认项；
- 整理执行记录、缺陷清单、回归结果和最终测试结论。

## 11. 开始测试前的最小信息包

开发不必一次提供全部资料。取得以下信息即可开始第一轮正常链路测试：

- [ ] 测试环境名称和当前版本；
- [ ] 已配置可用 Token，并告知配额；
- [ ] XXL-JOB 中两个 Job 的位置及操作权限；
- [ ] 一个测试账号、测试电站、plant ID/SN；
- [ ] 该电站的 `plants.block_id` 查询方法；
- [ ] 停电时刻表表名、字段和只读查询 SQL；
- [ ] APP/rice 查看停电计划的页面路径；
- [ ] 通知、强充、恢复的观察入口；
- [ ] 通知提前量、强充触发时间和恢复规则。
