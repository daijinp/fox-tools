## 2. 结论先行

1. **v2.0 将于 2026-09-01 停止服务。**截至本文整理日 2026-08-19，距离官方下线日仅 13 天，应把升级链路、回滚/止损及上线后观察作为 P0。
2. **本次目标仍是 v3.0，不是 v3.1。**升级通知同时宣传 v3.1 Beta；v3.1 新增社区众包故障报告和聊天摘要，不是现有“停电计划入库、通知、强充”需求的必需能力。
3. **3.0 的核心破坏性变化是 Area 与 Schedule 分离。**区域 ID 使用下划线，例如 `za_gt_jhb_fourways_4pef`；时刻表 ID 使用短横线，例如 `eskde-10`。
4. **旧 v2 区域 ID 可按官方提示提取时刻表部分。**例如 `eskde-10-fourways` → `eskde-10`，再请求 `/schedule`。对本项目来说，不修改存量 `block_id`，只在代码中转换，是保持数据库和下游兼容的关键。
5. **`/area` 不再承担“返回完整停电计划”的职责。**它返回区域基本信息及可用 `schedules`；真正的 `events` 和原始时刻表在 `/schedule`。
6. **所有业务接口都通过请求头 `token` 认证，不是 Bearer Token。**每个常规接口请求消耗 1 个 API credit。
7. **成功响应带 `x-ratelimit-*` 配额头。**日配额在 `00:00 UTC` 重置，即中国标准时间 08:00、南非标准时间 02:00；应使用 `x-ratelimit-reset` 决定 429 后何时重试。
8. **`/schedule?test=current|future` 不消耗配额，但官方只明确其在 `events` 中返回样例事件。**它适合验证“当前/未来事件”处理，不足以单独覆盖本项目对原始 `schedule` 槽位的转换。
9. **官方文档主要给示例，未给完整字段 Schema。**客户端解析应允许可选字段、动态市政键和空数组，不应只按单个示例写死。

## 3. 官方升级通知整理

### 3.1 v2.0 下线时间

- 官方通知发布时间：2026-06-10。
- v2.0 停止服务日期：**2026-09-01**。
- 下线前必须完成 v3.0 迁移；否则仍调用 `/business/2.0/...` 的任务将在下线后不可用。

测试和上线检查时，应搜索并确认：

- 生产配置、代码常量、定时任务、脚本中不再存在业务使用中的 `/business/2.0/` URL；
- 没有旁路脚本、临时任务或手工操作仍依赖 v2；
- 失败告警能够区分“旧版本已下线”和普通网络异常。

### 3.2 官方快速迁移提示

官方示例：

```text
v2 area ID:     eskde-10-fourways
v3 schedule ID: eskde-10
```

项目文档把它实现为“取旧 `block_id` 的前两段”。测试时不能只验证一个示例，应至少覆盖：

- 正常标准 ID；
- 多个旧 `block_id` 映射到同一个 schedule ID；
- 空值、少段、前后空白、连续分隔符、下划线 ID、大小写异常；
- 市属/Eskom Direct 等不同前缀的存量 ID；
- 转换失败时不发起错误请求、不覆盖旧数据。

> 项目文档称已核查全部非空存量 `block_id` 均为标准 v2 格式。该结论属于项目实测记录，上线前仍建议用生产只读 SQL 重新统计并保留结果。

### 3.3 v3.1 Beta 与本次范围

升级通知还宣布了 v3.1 Beta，新增社区众包 outage reports 和 chat highlights。3.0 官方首页也提示 v3.1 已提供，并建议在 3.1 中从 `x-ratelimit-*` 响应头读取配额。

本次测试应明确：

- 当前改造目标 URL 是 `/business/3.0/...`；
- 不因通知标题含“3.1”而把 `/reports` 或 `/chats` 纳入本次必测范围；
- 若配置或代码意外切到 `/business/3.1/`，需按需求变更处理，不能默认等价。

## 4. API 3.0 通用约定

### 4.1 基础信息

| 项目 | 官方约定 | 测试关注点 |
| --- | --- | --- |
| Base Path | `/business/3.0` | 确认环境配置没有残留 2.0，也没有误切 3.1 Beta |
| 请求方法 | 本文涉及接口均为 `GET` | 无副作用；重试不能造成数据库重复写入 |
| 认证 | Header：`token: <API_TOKEN>` | 缺失、空值、错误、失效 Token；日志和报告脱敏 |
| 成功响应 | HTTP 200，JSON | Content-Type、JSON 可解析、字段缺失/空数组兼容 |
| 集合响应 | 使用资源名包裹，如 `{"areas": [...]}` | 不能把顶层对象误当数组 |
| 单资源响应 | `area`、`schedule` 的字段位于顶层 | 不能按 v2 旧包装结构解析 |
| 常规计费 | 每个接口请求 1 API credit | 批量请求、重试和调度频率不能超额 |
| 免费测试 | `/schedule` 的 `test=current`、`test=future` | 只明确影响 `events`；不替代 raw schedule 槽位测试 |

### 4.2 配额与限流

每个成功响应应提供：

| 响应头 | 含义 | 建议校验 |
| --- | --- | --- |
| `x-ratelimit-limit` | 当前配额周期的总 credit | 能解析为非负数；与账号套餐相符 |
| `x-ratelimit-remaining` | 当前周期剩余 credit | 正常请求后应合理减少；并发时不要断言严格逐次减 1 |
| `x-ratelimit-used` | 当前周期已使用 credit | 与 remaining/limit 关系合理 |
| `x-ratelimit-reset` | 配额重置时刻，ISO 8601 UTC 时间戳 | 能解析时区；429 重试调度使用此值，不使用固定睡眠 |

官方列出的典型日配额：Personal 50、Professional 200、Enterprise Tier 1 2,500，其他企业档位更高。项目文档记录真实 Token 的配额为 2,500/天，但账号套餐和额度可能调整，应以当前响应头为准。

其他限制：

- 官方未公布独立的每分钟限额，但仍要求对突发流量使用合理的 jitter/backoff；
- 额度耗尽后，计费请求返回 429，且失败请求不会继续消耗 credit；
- 日配额在 `00:00 UTC` 重置；月配额在每月 1 日 `00:00 UTC` 重置；
- Token 可能因凭证共享、滥用、影响服务稳定性的自动流量或违反许可而被禁用；
- 不应为了压测直接消耗生产 Token。接口性能测试需先获得配额和供应商许可。

### 4.3 错误响应

统一错误体：

```json
{"error": "<message>"}
```

| 状态码 | 官方含义/出现位置 | 测试建议 |
| --- | --- | --- |
| 400 | 参数或 ID 格式错误、非法坐标 | 不重试；记录脱敏后的参数类别 |
| 401 | OpenAPI 各接口定义为 Token 缺失或无效 | 不重试；触发凭证告警 |
| 403 | 3.0 总览列为可能错误，但具体操作表未逐项列出 | 作为 Token 权限/禁用场景处理，不盲目重试 |
| 404 | Area 或 Schedule 不存在 | 单条不覆盖旧数据；批量 404 触发止损 |
| 429 | 配额耗尽 | 不立即重试；读取 reset 头并暂停/延后 |
| 500 | 3.0 总览列为可能错误 | 可做有限次数、带退避的重试；最终失败保留旧数据 |

> 文档差异：总览列出的错误包含 403/500，而各 endpoint 的 OpenAPI 表主要列 401/429，部分接口再列 400/404。测试不能假设所有错误都被接口表穷举。

## 5. 接口速查与字段说明

### 5.1 `GET /business/3.0/status`

用途：返回南非国家级以及可选市政覆盖的当前和下一阶段停电状态。

请求：

```http
GET /business/3.0/status
token: <MASKED_TOKEN>
```

官方示例的结构要点：

```json
{
  "status": {
    "eskom": {
      "name": "Eskom",
      "stage": "0",
      "stage_updated": "<ISO 8601 timestamp>",
      "next_stages": []
    },
    "capetown": {
      "name": "Cape Town",
      "stage": "0",
      "stage_updated": "<ISO 8601 timestamp>",
      "next_stages": []
    }
  }
}
```

字段与测试关注点：

- `status.eskom` 是国家级状态；这是项目停电通知使用的核心值。
- `status` 下其他 key 是市政覆盖，`capetown` 只是最常见示例；不应把所有 key 固定成 DTO 必填字段。
- 官方示例中 `stage` 是字符串，不是整数。至少覆盖 `"0"`、`"1"`～`"8"`、缺失/非法值的容错策略。
- `next_stages` 允许空数组；官方 3.0 文档没有提供其中对象的完整 Schema。
- `stage_updated` 是带时区偏移且可能含小数秒的时间戳。
- 项目文档称 3.0 与 2.x 的 status 结构完全一致、现有 DTO 无需改动。这是项目实测结论，应通过 2.x 留档 fixture 与 3.0 实际响应做回归对比。

### 5.2 `GET /business/3.0/areas_search?text=...`

用途：按文本搜索区域。

参数：`text`，string，必填。

响应结构：

```json
{
  "areas": [
    {
      "id": "za_gt_jhb_fourways_4pef",
      "name": "Fourways",
      "province": "Gauteng",
      "municipality": "City of Johannesburg"
    }
  ]
}
```

关键变化：

- v3 Area ID 使用下划线；
- 官方示例字段是 `id/name/province/municipality`，不再提供项目旧逻辑依赖的 `region`；
- 多个重名区域可能同时返回，不能仅按 `name` 取唯一结果；
- 空结果应按 `{"areas": []}` 处理。

项目决定将 `addregion` 在 job 入口和 service 层双重硬禁用，原因正是它依赖旧 `region` 并会把新 ID 写入存量区域树。测试重点不是验证它“还能同步”，而是验证任何入口都明确失败且数据库无写入。

### 5.3 `GET /business/3.0/areas_nearby?lat=...&lon=...&text=...`

用途：按 GPS 坐标查询附近区域。

| 参数 | 必填 | 类型 | 说明 |
| --- | --- | --- | --- |
| `lat` | 是 | number | 纬度 |
| `lon` | 是 | number | 经度 |
| `text` | 否 | string | 对附近结果进一步按文本过滤 |

官方说明第一条通常是与坐标最接近、最合适的区域，但使用“typically”，不是绝对排序契约。需覆盖：

- 正常南非坐标；
- 坐标边界、非数字、缺参和越界值；
- 有/无 `text`；
- 空结果、多个结果、重名结果；
- 400、401、429。

本项目存量主链路没有使用该接口，可作为 3.0 API 完整性测试的 P1，而不是发布阻塞项。

### 5.4 `GET /business/3.0/area?id=...`

用途：用 v3 Area ID 查询区域基本信息和可用时刻表列表。

参数：`id`，必填，使用下划线格式，例如 `za_gt_jhb_orlandoeast_bi73`。

响应结构：

```json
{
  "id": "za_gt_jhb_orlandoeast_bi73",
  "name": "Orlando East",
  "province": "Gauteng",
  "municipality": "City of Johannesburg",
  "schedules": [
    {"id": "eskde-14", "type": "loadshedding", "auto_enabled": true},
    {"id": "eskomgautenglr-f", "type": "load_reduction", "auto_enabled": true}
  ]
}
```

字段与边界：

- `schedules[].id` 才是调用 `/schedule` 的 ID；它使用短横线。
- `schedules[].type` 示例包括 `loadshedding` 和 `load_reduction`，不能把所有时刻表都当作 Stage 1～8 的 loadshedding。
- `auto_enabled` 在官方示例的某一项中缺失，说明客户端至少应允许该字段不存在。
- 把带短横线的 schedule ID 传给 `/area`，官方定义返回 400。
- 未找到返回 404；无效/缺失 Token 返回 401；额度耗尽返回 429。

本项目基于存量 v2 `block_id` 直接推导 schedule ID，因此核心入库链路不需要先请求 `/area`。这能节省配额，但必须依赖存量 ID 质量核查。

### 5.5 `GET /business/3.0/schedule?id=...&test=...`

用途：返回某个时刻表的近期事件和完整原始时刻表，是本次升级最关键的新接口。

参数：

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 短横线格式的 schedule ID，例如 `eskde-10` |
| `test` | 否 | 仅允许 `current` 或 `future` |

结构摘要：

```json
{
  "events": [
    {
      "note": "Stage 2",
      "start": "<ISO 8601 timestamp>",
      "end": "<ISO 8601 timestamp>"
    }
  ],
  "name": "Eskom Direct Block 10",
  "schedule": {
    "days": [
      {
        "date": "YYYY-MM-DD",
        "name": "Tuesday",
        "schedule": [
          {
            "name": "Stage 1",
            "slots": [
              {"start": "<ISO 8601 timestamp>", "end": "<ISO 8601 timestamp>"}
            ]
          }
        ]
      }
    ]
  }
}
```

字段语义：

- `events`：按时间排序的近期事件；`note` 表示 `Stage 2` 或 `Load Reduction` 等类型；每项有 `start/end`。
- `name`：时刻表名称。
- `schedule.days[]`：按日组织的原始时刻表。
- `days[].date`：所属日期；`days[].name` 是星期名称。
- `days[].schedule[]`：某日的阶段/类型条目。
- `schedule[].name`：例如 `Stage 1` 或 `Load Reduction`。
- `slots[]`：完整、带时区偏移的起止时间戳。

测试参数：

- `test=current`：在 `events` 中返回一个正在发生的样例 loadshedding 事件；
- `test=future`：在 `events` 中返回一个下一整点开始的样例事件；
- 两种测试请求均不消耗 API credit；
- 官方没有承诺 `test` 会构造满足所有 Stage、跨天和非法输入场景的 raw `schedule`，因此转换器仍需使用本地 fixture/Stub 完整测试。

错误：

- 把下划线 Area ID 传给 `/schedule`，官方定义返回 400；
- 不存在的 schedule ID 返回 404；
- Token 问题返回 401；额度耗尽返回 429。

### 5.6 `GET /business/3.0/api_allowance`（已弃用）

用途：返回 `allowance.count/limit/type`。该接口本身不消耗 API credit，但已被官方标记 deprecated，未来会删除。

后续实现和测试应以任意成功响应中的 `x-ratelimit-*` 头为准，不要新增对 `/api_allowance` 的依赖。若当前代码仍调用它，应登记技术债和替换计划。

## 6. v2 → v3 变化对照

| 主题 | v2/旧行为 | v3.0 | 对本项目的影响 |
| --- | --- | --- | --- |
| API 路径 | `/business/2.0/...` | `/business/3.0/...` | 所有运行中配置和常量必须切换 |
| Area ID | 短横线，例如 `eskde-10-fourways` | 下划线，例如 `za_gt_jhb_fourways_4pef` | 新 Area ID 不能直接写入依赖旧 ID 等值 JOIN 的存量库 |
| Schedule ID | 未作为独立概念使用 | 短横线，例如 `eskde-10` | 从旧 block ID 转换后请求 `/schedule` |
| `/area` | 项目旧链路从中取得计划 | 仅区域信息和 schedules 列表 | 原调用方必须迁移 |
| `/schedule` | 无 | 返回 events 和 raw schedule | 本次新增主接口 |
| `/areas_search` | 项目旧逻辑依赖 `region` | 示例为 `province/municipality`，ID 变更 | `addregion` 继续运行会破坏存量数据，应硬禁用 |
| `/status` | 国家/市政 Stage | 3.0 仍返回相同用途结构 | 项目要求 DTO 和业务行为不变，但需回归 |
| 配额读取 | 可调用 allowance | 响应头为长期方向，allowance 已弃用 | 客户端需正确采集并脱敏记录限流信息 |

## 7. 与项目实现方案的对应关系

| 项目要求/设计 | 官方依据 | 测试验收核心 |
| --- | --- | --- |
| 旧 `block_id` 不迁库 | 官方允许从 v2 ID 提取 v3 schedule ID | 原 ID 不变；rice 等值 JOIN 和 APP 展示无回归 |
| 新增 `/schedule` | 3.0 将 Schedule 独立为资源 | URL、ID、响应解析、错误处理正确 |
| schedule ID 去重请求 | 每次请求消耗 1 credit | 相同 schedule ID 每轮仅请求一次，结果回填所有原 block ID |
| 3.0 slots 转旧 8 级二维数组 | 官方 raw schedule 按 days/stage/slots 返回 | Stage 1～8、累加并集、排序、去重、跨天和非法数据拒收 |
| 失败保留旧数据 | 官方存在 400/401/403/404/429/500 | 任一份 schedule 非法/请求失败时不写空、不写半份、不覆盖旧值 |
| 5xx 重试 2 次 | 项目容错设计 | 仅可重试错误重试；总次数、退避、最终失败行为和幂等性正确 |
| 解析限流头 | 官方推荐 `x-ratelimit-*` | 正常/缺头/非法头/429 均不导致任务级异常扩散 |
| Token 不入日志 | 官方要求 Token 私密 | 请求日志、异常、APM、测试报告、CI 输出全链路脱敏 |

## 9. 转换器专项测试数据建议

转换器应以本地 fixture/Mock 为主，避免消耗真实配额并获得确定性。

| 数据类别 | 示例/构造方式 | 预期 |
| --- | --- | --- |
| 单 Stage 单槽 | Stage 1 一个日内槽 | 8 级结构存在，Stage 1～8 均含该槽 |
| 多 Stage | Stage 1、2 各有不同槽 | Stage 2 及以上为前序阶段并集 |
| 上游已累加 | Stage 2 重复包含 Stage 1 槽 | 输出去重，不产生重复时间段 |
| 同级乱序 | slots 输入顺序打乱 | 输出按业务约定稳定排序 |
| 日内槽 | `10:00-12:30` | 输出同日 `HH:mm-HH:mm` |
| 跨午夜 | 当日 20:00 → 次日 00:30 | 输出 `20:00-00:30`，下游识别跨天 |
| 零点边界 | 当日 00:00 开始或次日 00:00 结束 | 不误判日期，不丢槽 |
| 时区偏移 | 带 `+02:00`、其他合法 offset、小数秒 | 按明确的业务时区规则转换，不按服务器本地时区漂移 |
| 空数组 | 某日/某 Stage 无 slots | 输出结构完整且无脏数据 |
| Stage 0/9/文本异常 | 非 1～8 的 stage name | 整份响应拒收并保留旧数据 |
| 非法时间 | 缺 offset、不可解析、end ≤ start | 按约定拒收；不得部分写入 |
| 跨两天 | end 超过次日 | 拒收，因旧 `HH:mm-HH:mm` 结构无法表达 |
| 日期不一致 | slot 与 `days[].date` 不匹配 | 拒收或按明确规则处理，不静默错日 |
| Load Reduction | `name=Load Reduction` | 不误入 Stage 1～8 转换链路 |

> 时区特别说明：官方示例只说明时间戳带 offset，示例 offset 不应被当成固定业务时区。测试应验证代码尊重时间戳中的 offset，并与项目规定的入库时区一致。

## 11. 已发现的资料问题与待确认项

### 11.1 官方资料中的注意点

1. **错误码口径不完全一致。**总览含 400/403/404/429/500，具体接口表主要列 401/429 及部分 400/404；需要以联调结果完善契约。
2. **OpenAPI 没有完整对象 Schema。**当前主要依赖 example，不能据此认定每个示例字段必填。
3. **`auto_enabled` 示例中存在缺失。**解析时应按可选字段处理。
4. **Schedule 示例的 `date` 与星期 `name` 存在不一致。**示例中 `2026-11-18` 实际是 Wednesday，但 `name` 写为 Tuesday。业务日期计算应以可解析时间戳和 `date` 为准，不应依赖英文星期文本。
5. **`test` 参数只明确影响 `events`。**不能据此证明 raw schedule 的 Stage 累加、跨天等逻辑正确。
6. **限流头主要通过文字说明。**OpenAPI 各 200 response 没有逐项声明 header schema；应做缺头/非法头容错。

### 11.2 项目技术文档的待补信息

1. 原文存在重复表格行、“0 个结果”“加载中”等导出残留，系统全景图和两条业务链路图未实际呈现。
2. “相关查询 SQL”章节只有占位代码块，没有可执行 SQL；上线验收前必须补齐并评审只读/写入安全性。
3. 当前工作区仅包含技术文档，没有文中所述 Java 改动、6 个测试类、2 个 fixture 和 CI 配置，本文无法核实代码是否与方案一致。
4. “72 个 schedule 全部 HTTP 200”“配额 2,500/天”“4,183 条 block_id 全覆盖”等属于历史实测结果，需要保留可追溯的查询结果、执行日期和环境。
5. “3.0 `/status` 与 2.x 完全一致”属于项目实测，而不是官方给出的长期兼容承诺；建议保留契约 fixture。
6. 需要补充各任务的实际 cron、单轮理论最大请求量、重试后的最坏额度消耗和告警阈值。
7. 需要明确转换失败的事务边界：按单 schedule、单 block 还是整轮回滚；测试断言依赖这一约定。
